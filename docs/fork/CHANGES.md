# What differs from upstream xsdata

This is the docx4j-python fork of [tefra/xsdata](https://github.com/tefra/xsdata) (MIT).
Upstream's own changelog stays at [`CHANGES.md`](../../CHANGES.md) in the repository
root and is never edited by the fork; this file records only the delta.

Current base: **upstream `v26.2`** (`7a82d771bbdddee2fb6ef0facf95979c426a0531`).
See [REBASING.md](REBASING.md) for how that base moves.

The rationale for the fork, and the whole plan, is CR-001 section 4 in the
docx4j-python repository (`docs/change-requests/CR-001-object-model.md`).

## Stage 1 — the rename (done)

One script-generated commit, `tools/rename.py`. Nothing in it is hand-edited, so a new
upstream tag is adopted by re-running the script rather than by rebasing the rename.

| | upstream | fork |
|---|---|---|
| distribution | `xsdata` | `docx4j-xsdata` |
| import package | `xsdata` | `docx4j_xsdata` |
| console script | `xsdata` | `docx4j-xsdata` |
| plugin groups | `xsdata.plugins.cli`, `xsdata.plugins.class_types` | `docx4j_xsdata.plugins.cli`, `docx4j_xsdata.plugins.class_types` |
| generated bindings import | `from xsdata.models.datatype import ...` | `from docx4j_xsdata.models.datatype import ...` |
| generated file header | `generated by xsdata, v26.2` | `generated by docx4j-xsdata, v26.2` |
| CLI banner | `========= xsdata v26.2 ...` | `========= docx4j-xsdata v26.2 ...` |
| schema download cache | `/tmp/xsdata.<version>.<hash>.cache` | `/tmp/docx4j-xsdata.<version>.<hash>.cache` |
| HTTP User-agent | `xsdata/<version>` | `docx4j-xsdata/<version>` |
| CI | tests, W3C tests, benchmarks, pre-commit, codecov, PyPI publish | tests (3.10–3.14) and the minimum-install check only |

The point of the rename is coexistence: the fork's runtime installs alongside upstream
`xsdata` in one environment, and generated bindings import their runtime types from
`docx4j_xsdata`. Upstream's plugin ecosystem (`xsdata-pydantic`, `xsdata-attrs`,
`xsdata-plantuml`) does not attach to the renamed entry-point groups, which is intended.

### Deliberately *not* renamed

| Kept | Why |
|---|---|
| `http://pypi.org/project/xsdata` | the generator config XML namespace; existing `.xsdata.xml` files must keep validating |
| `.xsdata.xml` | the default config file name, same reason |
| bare `"xsdata"` string literals | ~1,400 of them are an arbitrary XML namespace URI in tests and fixtures (`{xsdata}root`, `targetNamespace="xsdata"`); they have nothing to do with the package name |
| URLs containing `xsdata` | links to upstream's repo, docs, PyPI page and W3C suite point at upstream, which is where that material is |
| root `CHANGES.md` | upstream's historical changelog |
| prose in `docs/` | "xsdata is using python's dataclasses…" describes the same software; renaming prose is churn and rebase noise |
| `docs/logo.svg`, `docs/logo-small.svg`, `docs/robots.txt` | upstream branding and the readthedocs sitemap |
| `LICENSE` | unchanged, upstream MIT, Christodoulos Tsoulloftas. The MIT text requires no extra notice for the fork's changes; the fork's own copyright (Plutext Pty Ltd, 2026) is noted in the README |

### Non-obvious consequences of a longer name

`docx4j_xsdata` is seven characters longer than `xsdata` and sorts differently, so:

* **Import order moves.** `docx4j_xsdata` sorts before `tests`, `toposort` and `typing`
  where `xsdata` sorted after them. `tools/rename.py` re-sorts exactly the import blocks
  that mention the renamed package, and reorders the four affected expectations by hand-
  written rule: the `PycodeSerializer` output in
  `tests/formats/dataclass/serializers/test_code.py` and
  `docs/data_binding/pycode_serializing.md`, and the two committed fixtures the test
  suite regenerates (`tests/fixtures/books/fixtures.py`, `tests/fixtures/primer/sample.py`).
* **Some imports cross the 88-character line limit.** The script wraps those in the
  parenthesised, one-name-per-line form ruff's isort produces.

Result: `ruff check` reports exactly the same 34 findings on the fork as on upstream
`v26.2` (all of them in `tests/fixtures`, and all of them pre-existing with a newer ruff
than upstream pins), and `ruff format --check` the same 6 files. `tools/` is added to
ruff's exclude list; it is fork-owned and not subject to upstream's docstring conventions.

### Test status

`pytest --doctest-glob="docs/*.md"` on CPython 3.14.6:

| | result |
|---|---|
| upstream `v26.2` | 1103 passed, 17 skipped |
| the fork after the rename | 1103 passed, 17 skipped |

### Verified against the real project

`docx4j-xsdata generate -c .xsdata.xml schemas/wml/wml.xsd` in docx4j-python, with the
output package redirected to `docx4j_py.generated_fork`:

* 1,624 modules generated in 4.6 s, the same 6 upstream warnings as unmodified xsdata
* the only runtime import in the output is `from docx4j_xsdata.models.datatype import ...`
  (5 modules); no `xsdata` import anywhere
* the package imports in 0.90 s / 1,731 modules, matching the REPORT.md baseline of
  0.86 s / 1,755 modules
* `word/document.xml` of a real sample parses to a `Document` through the fork's
  `XmlParser` with the `LxmlEventHandler`

## Stage 2 — the generator changes (not yet done)

CR-001 section 3 and phase A of section 10. All four are generator-side
(`docx4j_xsdata.codegen`, `docx4j_xsdata.formats.dataclass.filters`) and all are
configuration flags that **default to upstream behaviour**, so the fork can still
generate ordinary bindings:

1. **Optional everything.** Every element and attribute generated as
   `Optional[...] = None`, so schema-required members are not mandatory constructor
   arguments. Real Word documents are schema-invalid and must still load.
2. **Defaults on read.** `default=None` in the dataclass with the schema default kept
   in the field metadata, so the serialiser neither invents 5,516 absent attributes
   nor drops 773 present ones.
3. **List factory.** Emit `default_factory=ChildList` rather than `default_factory=list`
   for every list field, so appending a child sets its parent pointer.
4. **Circular-import fix** for `--structure-style namespaces`: postponed annotations
   and `TYPE_CHECKING` imports so per-namespace packages with cross-namespace cycles
   import. This one is an upstream candidate (report 1 above).

Where that work lands:

* field generation and the emitted `field(...)` call: `docx4j_xsdata/formats/dataclass/filters.py`
* the generator config model (where new flags are declared, and the `.xsdata.xml`
  schema they serialise into): `docx4j_xsdata/models/config.py`
* import collection and ordering for a generated module:
  `docx4j_xsdata/codegen/resolver.py` and `docx4j_xsdata/formats/dataclass/filters.py`
* module/package layout decisions: `docx4j_xsdata/codegen/handlers/designate_class_packages.py`
* the jinja templates: `docx4j_xsdata/formats/dataclass/templates/` (note that these
  contain no `xsdata` literal of their own — the imports emitted into generated code
  are built in `filters.py`)
