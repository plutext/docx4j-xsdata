# Rebasing the fork onto a new upstream tag

## Where the fork currently sits

| | |
|---|---|
| Upstream tag | `v26.2` (2026-02-15) |
| Upstream commit | `7a82d771bbdddee2fb6ef0facf95979c426a0531` |
| Fork branch | `docx4j` |
| Remotes | `upstream` = <https://github.com/tefra/xsdata>, `origin` = <https://github.com/plutext/docx4j-xsdata> |

Update this table every time `tools/rebase-upstream.sh` is run.

## The shape of the branch

```
upstream v26.2
  └─ Fork tooling: rename script, rebase script, fork docs      <- tools/, docs/fork/
      └─ Rename to docx4j_xsdata (generated by tools/rename.py) <- 100% script output
          └─ ... our feature commits (generator flags, etc.) ...
```

Two properties make rebasing cheap:

1. **The rename is never rebased, it is regenerated.** It is one commit whose entire
   content is the output of `tools/rename.py` run on a pristine upstream checkout.
   Replaying it onto a new tag would conflict in every file upstream touched; running
   the script again conflicts in none.
2. **The tooling commit sits *below* the rename commit,** so it is inside the base
   that the new branch is built from, and the rebase never has to replay it.

## The procedure

```console
$ tools/rebase-upstream.sh v26.3
```

which is exactly:

```console
$ git fetch upstream --tags
$ git checkout -b upstream-renamed-v26.3 v26.3
$ git checkout docx4j -- tools docs/fork          # tooling must be in the base
$ git commit -m "Fork tooling: rename script, rebase script, fork docs"
$ python3 tools/rename.py .
$ git add -A && git commit -m "Rename to docx4j_xsdata (generated by tools/rename.py)"
$ git rebase --onto upstream-renamed-v26.3 <old rename commit> docx4j
```

`<old rename commit>` is found automatically by the script: it is the newest commit
on `docx4j` whose subject is `Rename to docx4j_xsdata (generated by tools/rename.py)`.

Useful flags:

* `--no-rebase` builds `upstream-renamed-$TAG` and stops, for inspection.
* `--branch NAME` overrides the branch name (used by the self-test below).

## Expected conflict behaviour

* **The rename itself never conflicts.** It is regenerated, not replayed.
* **`tools/rename.py` fails loudly instead of renaming wrongly.** Every one of its
  per-file replacements is checked: a `required` rule whose upstream text has moved
  or changed makes the script exit 3 with the file and the text it looked for. That
  is the signal that upstream refactored something the fork names explicitly (the CLI
  banner, the generated-file header, `pyproject.toml`, the ruff/coverage paths). Fix
  the rule, re-run.
* **The leftover report is the second net.** After renaming, the script scans every
  file it processed and prints any remaining `xsdata` that still looks like a module
  path, a package path or a pip extra. It should print `0`. A non-zero count after a
  new upstream release means upstream introduced a new spelling; add a rule.
* **Our feature commits conflict normally**, in the ordinary rebase way, and only
  where upstream changed the same lines. The files to expect them in are the ones
  Phase B touches: `docx4j_xsdata/formats/dataclass/filters.py`,
  `docx4j_xsdata/models/config.py`, `docx4j_xsdata/codegen/`.
  Resolve, `git rebase --continue`.
* **A conflict inside `docx4j_xsdata/...` paths is normal and harmless**: our commits
  were written against the renamed tree and the new base is also renamed, so paths
  match.

## After a rebase

1. Update the table at the top of this file.
2. Add a section to `docs/fork/CHANGES.md`.
3. `uv pip install -e '.[cli,lxml,soap,test]'` and
   `pytest --doctest-glob="docs/*.md"` — it must be as green as upstream's own tag.
4. `git branch -D upstream-renamed-$TAG` once satisfied.
5. Publish: `git push --force-with-lease origin docx4j`, then tag and push a release
   (see [Publishing](#publishing)).

## Branches and remotes

The fork lives at <https://github.com/plutext/docx4j-xsdata>, a GitHub fork of
<https://github.com/tefra/xsdata>.

| Remote | Points at | Used for |
|---|---|---|
| `upstream` | tefra/xsdata | fetching upstream tags. `tools/rebase-upstream.sh` fetches from this name, so do not rename it. |
| `origin` | plutext/docx4j-xsdata | publishing the fork. |

| Branch | Contents | Rule |
|---|---|---|
| `main` | An exact mirror of `upstream/main`. | **Never commit to it or merge `docx4j` into it.** Update it only by fast-forwarding (`git pull upstream main`, or GitHub's "Sync fork" button). |
| `docx4j` | The fork: tooling, rename and feature commits on an upstream tag. | The GitHub default branch. Rewritten on every rebase. |

Why `docx4j` is never merged into `main`:

* `docx4j` is maintained by rebasing, not merging. Each new upstream tag gets a
  regenerated rename commit and the feature commits are replayed on top, so the
  branch history is rewritten each time. A merge into `main` would make the next
  rebase bring in duplicate commits and conflicts.
* `docx4j` sits on a release tag, while `upstream/main` moves ahead of it with commits
  written against the un-renamed `xsdata/` paths. Merging the two means reconciling
  those commits with a rename that touches every file, which is exactly the conflict
  that regenerating the rename exists to avoid.
* A clean `main` keeps "Sync fork" working and makes upstream changes easy to diff.

GitHub forks default new pull requests to target `tefra/xsdata`. Check the base
repository when opening a PR.

## Publishing

Because every rebase rewrites `docx4j`, pushing it after a rebase needs a force push:

```console
$ git push --force-with-lease origin docx4j
```

`--force-with-lease` refuses to push if `origin/docx4j` has commits you have not
fetched, so a rebase cannot silently discard someone else's push. An ordinary feature
commit on top of an unchanged base needs only a normal `git push`.

Rewriting the branch means a commit hash on `docx4j` is not a stable reference: after
the next rebase it no longer lies on the branch. Anything that depends on the fork (the
docx4j build, a pinned `pip install git+...`) must therefore pin a **tag**, never the
branch or a bare commit. Tag each published state:

```console
$ git tag -a docx4j-v26.2.1 -m "docx4j_xsdata on upstream v26.2, fork release 1"
$ git push origin docx4j-v26.2.1
```

Tag naming: `docx4j-v<upstream tag>.<fork release>`. The fork release number counts
up from 1 on each upstream tag and resets when the fork moves to a new upstream tag.
Tags are never moved or deleted: the tagged commits stay reachable through the tag
after the branch has been rewritten.

## Self-test

The script can be exercised without a newer upstream tag by pointing it at the tag
the fork already sits on and comparing the trees:

```console
$ tools/rebase-upstream.sh v26.2 --branch scratch-renamed --no-rebase
$ git diff --stat scratch-renamed docx4j        # must be empty
$ git branch -D scratch-renamed
```

An empty diff proves the rename is reproducible: the committed rename commit and a
freshly generated one from the same tag are byte-identical.

Both halves were exercised on 2026-09-12 against `v26.2`: the `--no-rebase` self-test
produced an empty tree diff against `docx4j`, and a full run in a throwaway clone (with
one dummy feature commit on top) replayed exactly that one commit onto a regenerated
base, leaving the tooling and rename commits regenerated rather than replayed.
